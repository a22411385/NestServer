# 配置服務泛型化方案對比

## 📊 三種方案完整對比

### 方案 1：完全泛型化類（最激進）

```typescript
// 實現
export class GenericConfigService<T extends { id: string; enabled?: boolean }> {
    constructor(private configKey: keyof GoogleCacheData) {}
    
    getAll(): T[] {
        const cache = BaseConfigService.loadCache();
        return (cache[this.configKey] || []) as T[];
    }
    
    getById(id: string): T | null {
        return this.getAll().find(item => item.id === id) || null;
    }
    
    getByField(field: keyof T, value: any): T[] {
        return this.getAll().filter(item => item[field] === value);
    }
}

// 使用方式
const ItemService = new GenericConfigService<ItemConfigDefinition>('ItemConfigs');
const items = ItemService.getAll();

// 或作為靜態實例
export const Items = new GenericConfigService<ItemConfigDefinition>('ItemConfigs');

// 在 ConfigManager 中
export class ConfigManager {
    public static Items = new GenericConfigService<ItemConfigDefinition>('ItemConfigs');
    public static Enemies = new GenericConfigService<EnemyConfigDefinition>('EnemyConfigs');
}
```

#### ✅ 優點

1. **代碼量最少**
   - 一個泛型類處理所有配置類型
   - 新配置只需一行：`new GenericConfigService<T>('Key')`

2. **類型安全**
   - 完整的類型推導
   - 編譯時檢查

3. **DRY原則**
   - 完全消除重複代碼
   - 統一的方法簽名

#### ❌ 缺點

1. **失去靜態方法便利性**
   ```typescript
   // 需要先獲取實例
   ConfigManager.Items.getAll()  // ❌ Items 是實例
   
   // vs 靜態方法
   ItemConfigService.getAll()    // ✅ 直接調用
   ```

2. **特殊方法難以處理**
   ```typescript
   // 如何處理 EnemyConfigService 的特殊方法？
   getByWave(wave: number)          // ❌ 不是所有配置都有 wave
   getRandomIdByWave(wave: number)  // ❌ 特殊邏輯
   ```

3. **需要實例化或導出實例**
   ```typescript
   // 方式A：每次實例化（不推薦）
   const service = new GenericConfigService<T>('Key');
   
   // 方式B：導出單例（需要額外代碼）
   export const Items = new GenericConfigService<T>('ItemConfigs');
   ```

4. **IDE 自動補全體驗差**
   - 無法直接看到可用方法
   - 需要查看泛型類定義

#### 📊 評分

| 項目 | 評分 | 說明 |
|------|------|------|
| 代碼量 | ⭐⭐⭐⭐⭐ | 最少 |
| 易用性 | ⭐⭐ | 需要實例化 |
| 靈活性 | ⭐⭐ | 特殊方法難處理 |
| 可維護性 | ⭐⭐⭐ | 集中但不夠靈活 |
| 類型安全 | ⭐⭐⭐⭐⭐ | 完整 |

### 方案 2：抽象泛型基類（TypeScript 限制）

```typescript
// 實現
export abstract class BaseConfigService<T extends { id: string }> {
    // ❌ TypeScript 不支持抽象靜態方法
    protected abstract getConfigKey(): keyof GoogleCacheData;
    
    // ❌ 必須是實例方法
    public getAll(): T[] {
        const cache = this.loadCache();
        return (cache[this.getConfigKey()] || []) as T[];
    }
    
    public getById(id: string): T | null {
        return this.getAll().find(item => item.id === id) || null;
    }
}

// 子類實現
export class ItemConfigService extends BaseConfigService<ItemConfigDefinition> {
    protected getConfigKey() {
        return 'ItemConfigs' as const;
    }
    
    // 特殊方法
    public getByNpcId(npcId: string): ItemConfigDefinition[] {
        return this.getAll().filter(item => item.npcId === npcId);
    }
}

// ❌ 使用需要實例化
const itemService = new ItemConfigService();
const items = itemService.getAll();
```

#### ✅ 優點

1. **繼承優勢**
   - 基類方法自動可用
   - 子類可以覆寫

2. **類型安全**
   - 泛型參數保證類型
   - 每個服務類有明確的類型

#### ❌ 缺點

1. **TypeScript 限制**
   - 不支持抽象靜態方法
   - 必須實例化使用

2. **靜態包裝複雜**
   ```typescript
   // 需要額外的靜態包裝層
   export class ItemConfigService {
       private static instance = new ItemConfigServiceImpl();
       public static getAll() { return this.instance.getAll(); }
   }
   ```

3. **不符合原設計**
   - 原本是靜態方法
   - 改為實例方法破壞一致性

#### 📊 評分

| 項目 | 評分 | 說明 |
|------|------|------|
| 代碼量 | ⭐⭐⭐ | 中等 |
| 易用性 | ⭐⭐ | 需要實例化或包裝 |
| 靈活性 | ⭐⭐⭐⭐ | 可以有特殊方法 |
| 可維護性 | ⭐⭐⭐ | 繼承複雜度 |
| 類型安全 | ⭐⭐⭐⭐⭐ | 完整 |

### 方案 3：泛型工具函數 + 靜態類（✅ 已實現）

```typescript
// 基類提供泛型工具方法
export abstract class BaseConfigService {
    protected static cache: GoogleCacheData;
    
    // 🆕 泛型工具方法
    protected static getConfigArray<T>(
        cache: GoogleCacheData,
        key: keyof GoogleCacheData
    ): T[] {
        return (cache[key] || []) as T[];
    }
    
    protected static findById<T extends { id: string }>(
        items: T[],
        id: string
    ): T | null {
        return items.find(item => item.id === id) || null;
    }
    
    protected static filterByField<T>(
        items: T[],
        fieldName: keyof T,
        value: any
    ): T[] {
        return items.filter(item => item[fieldName] === value);
    }
    
    // 更多泛型工具...
}

// 服務類使用泛型工具
export class ItemConfigService extends BaseConfigService {
    // 使用泛型工具，減少重複代碼
    public static getAll(): ItemConfigDefinition[] {
        return this.getConfigArray<ItemConfigDefinition>(this.loadCache(), 'ItemConfigs');
    }
    
    public static getById(id: string): ItemConfigDefinition | null {
        return this.findById<ItemConfigDefinition>(this.getAll(), id);
    }
    
    public static getByRarity(rarity: string): ItemConfigDefinition[] {
        return this.filterByField<ItemConfigDefinition>(this.getAll(), 'rarity', rarity);
    }
    
    // 特殊方法保持靈活性
    public static getByConditions(conditions: Partial<ItemConfigDefinition>) {
        return this.filterByConditions<ItemConfigDefinition>(this.getAll(), conditions);
    }
}

// 使用方式（完全靜態）
const items = ItemConfigService.getAll();
const sword = ItemConfigService.getById('iron_sword');

// 通過 ConfigManager 門面
const items = ConfigManager.Items.getAll();
```

#### ✅ 優點

1. **保持靜態方法**
   ```typescript
   // ✅ 無需實例化
   ItemConfigService.getAll()
   ConfigManager.Items.getAll()
   ```

2. **減少重複代碼**
   ```typescript
   // 通用邏輯在泛型工具中
   protected static findById<T>(items: T[], id: string)
   protected static filterByField<T>(items: T[], field, value)
   
   // 服務類只需調用
   return this.findById<ItemConfigDefinition>(this.getAll(), id);
   ```

3. **支持特殊方法**
   ```typescript
   // 每個服務可以有自己的特殊方法
   export class EnemyConfigService extends BaseConfigService {
       public static getByWave(wave: number) { /* ... */ }
       public static getRandomIdByWave(wave: number) { /* ... */ }
   }
   ```

4. **類型安全**
   ```typescript
   // 完整的類型推導
   const items: ItemConfigDefinition[] = ItemConfigService.getAll();
   ```

5. **IDE 友好**
   - 每個服務類方法清晰可見
   - 自動補全完美支持
   - 易於跳轉定義

6. **漸進式重構**
   - 不需要大改現有代碼
   - 逐步將重複邏輯提取到泛型工具

#### ⚠️ 注意事項

1. **泛型參數需要明確**
   ```typescript
   // 需要指定類型參數
   this.findById<ItemConfigDefinition>(items, id)
   
   // 不能省略（除非 TypeScript 能推導）
   this.findById(items, id) // 可能推導為 { id: string }
   ```

2. **仍有少量重複**
   ```typescript
   // 每個服務類仍需要包裝方法
   public static getAll() {
       return this.getConfigArray<T>(this.loadCache(), 'Key');
   }
   ```

| 易用性 | ⭐⭐⭐⭐⭐ | 完全靜態，無需實例化 |
| 靈活性 | ⭐⭐⭐⭐⭐ | 支持特殊方法 |

## 🎓 結論與建議

### ✅ 推薦：方案 3（已實現）

**理由**：
1. ✅ 完美平衡代碼重用和靈活性
2. ✅ 保持靜態方法便利性
3. ✅ 支持特殊方法（如 `getByWave`、`getRandomIdByWave`）
4. ✅ IDE 自動補全友好
5. ✅ 易於維護和擴展
6. ✅ 類型安全完整

**適用場景**：
- ✅ 配置類型多樣（有通用也有特殊）
- ✅ 需要靜態方法（無需實例化）
- ✅ 重視開發體驗（IDE 支持）
- ✅ 團隊協作（清晰的結構）

### ❌ 不推薦：方案 1（完全泛型）

**原因**：
- ❌ 失去靜態方法便利性
- ❌ 特殊方法難以處理
- ❌ IDE 體驗較差

**適用場景**：
- 僅適用於配置類型完全統一
- 不需要特殊方法
- 追求極致代碼量最小化

### ❌ 不推薦：方案 2（抽象基類）

**原因**：
- ❌ TypeScript 限制（不支持抽象靜態方法）
- ❌ 需要複雜的靜態包裝
- ❌ 破壞原有設計

   ```typescript
   // 緩存查詢結果
   private static resultCache = new Map();
   
   protected static memoize<T>(key: string, fn: () => T): T {
       if (!this.resultCache.has(key)) {
           this.resultCache.set(key, fn());
       }
       return this.resultCache.get(key);
   }
   ```

3. **添加驗證器**
